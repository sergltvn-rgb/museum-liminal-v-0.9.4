# Инструменты агента: как смотреть на игру

Этот файл описывает, как снимать и проверять сцену. Он существует потому, что
один раз это уже приходилось выяснять опытным путём, и второй раз выяснять то
же самое — потерянный заход.

## Проблема

Агент читает изображения одним вызовом `file_read_media(path)`. У вызова нет ни
качества, ни масштаба, ни постраничности — только путь. Он отваливается по
тайм-ауту на PNG тяжелее примерно половины мегабайта, а удачное чтение крупного
файла приходит обрезанным. Лимит живёт в клиенте, вне репозитория, поднять его
отсюда нельзя.

Единственная управляемая величина — вес файла. Поэтому чинить нужно не чтение,
а съёмку.

## Почему JPEG, а не PNG

Кадр 1920×1080 детализированной 3D-сцены весит 1.5–1.8 МБ в PNG: формат без
потерь, и каждая травинка процедурной текстуры — честная энтропия. Тот же кадр
в JPEG при 640 px и качестве 0.62 весит 28–38 КБ. Это в полсотни раз легче, а
для оценки архитектуры, посадок и света потери несущественны.

Важная деталь: ответ несёт одну и ту же base64-строку дважды — в `content` и в
`structuredContent`. Реальная нагрузка вдвое больше файла, и пороги в
`AgentShots.gd` уже это учитывают.

## AgentShots.gd

Сохраняет один кадр в трёх видах:

| путь | что это | вес |
|---|---|---|
| `<dir>/<имя>.png` | полное разрешение, без потерь — **для человека** | ~1.6 МБ |
| `<dir>/view/<имя>.jpg` | кадр целиком — **читаемая агентом копия** | ~30 КБ |
| `<dir>/tiles/<имя>_r0c1.jpg` | четверти кадра в исходной плотности пикселей | ~15–31 КБ |

Плитки — то, что возвращает детализацию, потерянную при уменьшении. Кроп
четверти кадра, ужатый до 640 px, сохраняет почти исходную плотность, поэтому
шов, z-fighting или щель между плитами крыши остаются видны. На уменьшенном
целом кадре именно это и пропадает.

Каждая запись сообщает свой вес, а всё, что тяжелее `READ_LIMIT_BYTES`,
помечается в логе: кадр, который нельзя открыть, хуже отсутствия кадра, потому
что выглядит как доказательство.

## test_shot.gd — съёмка любой точки без правки кода

Фиксированные капчеры (`test_exterior_capture`, `test_lobby_capture`, …) держат
ракурсы в константах: новая точка требовала правки массива, а проверка одного
подозрительного угла — пересъёмки восьми видов. Здесь список кадров лежит в
`agent_shots.json`, поэтому новый ракурс стоит одной записи в файл.

```json
{
  "scene": "res://scenes/FirstMuseumMap.tscn",
  "out_dir": "res://shots",
  "tiles": 2,
  "shots": [
    { "name": "court_axis", "pos": [0, 1.7, 52], "look_at": [0, 4, 36] },
    { "name": "roof_seam", "pos": [24, 12, 44], "rot": [-14, 62, 0], "fov": 40 }
  ]
}
```

- `look_at` наводит камеру на точку мира и почти всегда предпочтительнее: угадывать
  рыскание и тангаж руками — это заход на кадр.
- `rot` задаёт углы Эйлера явно, когда нужен конкретный поворот.
- `fov` сужает объектив: дешёвый способ рассмотреть деталь издалека, не влезая в
  ближнюю плоскость отсечения.
- `scene` позволяет снимать не только главную карту.

Запуск (**без** `--headless` — там нет фреймбуфера для чтения):

```
Godot_v4.7-stable_win64_console.exe --path . --script res://game/test_shot.gd
```

## Грабли

- **`--headless` для съёмки не годится**, кадр читать неоткуда. Для диагностики
  геометрии (`test_shell_intrusion.gd`) он, наоборот, нужен и ускоряет прогон.
- **`class_name` не виден при прямом `--script`.** Глобальные имена классов
  регистрирует сканирование проекта при импорте, а одиночный запуск скрипта его
  не делает. Поэтому `test_shot.gd` берёт помощника через `preload`, а не по
  имени `AgentShots`.
- **Камеру держит игрок.** У контроллера отключается `set_process` и
  `set_physics_process`, иначе кадр уползает обратно к голове персонажа.
- **`MenuManager` рисуется поверх 3D** и попадает в каждый кадр — удаляется.
- **`cam.far` расширяется до 4000**, иначе дальние массивы отсекаются на общих
  планах.
